# Production Readiness Assessment

The current KijaniKiosk deployment demonstrates several production-oriented Kubernetes practices, but it is not yet suitable for handling real customer payment traffic without additional controls.

**External routing:** The current NGINX Ingress successfully routes `/api` and `/payments`, but it exposes payment traffic over plain HTTP. This means credentials and other sensitive payment data could be intercepted or modified while travelling between clients and the Ingress. Production traffic should use HTTPS with a Kubernetes TLS Secret containing a valid certificate and the Ingress `spec.tls` configuration for `kijani.local`. The Ingress should also use the `nginx.ingress.kubernetes.io/ssl-redirect: "true"` annotation to force HTTP requests to HTTPS. TLS alone is not sufficient. Payment endpoints should also have rate limiting to reduce abuse and denial-of-service risk. With the NGINX Ingress Controller, annotations such as `nginx.ingress.kubernetes.io/limit-rps` can limit requests per second from individual clients. Authentication and authorization should also be enforced where appropriate rather than relying only on network routing.

**Health signalling:** The current probes provide basic availability detection, but payment services require conservative health settings because startup and database connectivity can take longer under production conditions. The readiness probe should have an initial delay long enough for the application and database connections to initialize, potentially increasing `initialDelaySeconds` from 5 seconds to 15–30 seconds. The readiness `failureThreshold` could also be increased from 3 if temporary database delays are expected. A failure threshold that is too low can repeatedly remove healthy payment Pods from Service endpoints during short database slowdowns, reducing capacity and potentially interrupting transactions. Liveness should be less aggressive because restarting a payment service during a temporary dependency problem could make an incident worse.

**Capacity:** Three manually managed replicas are not sufficient for predictable end-of-month traffic spikes. Autoscaling should use Kubernetes Metrics Server and accurate CPU/memory resource requests so that an HPA can make meaningful scaling decisions. An HPA could target CPU utilization, for example 60–70%, with minimum and maximum replica limits. If the CPU target is set too high, Pods may become overloaded before Kubernetes adds capacity, causing increased latency or failed requests. If it is set too low, the HPA may scale out unnecessarily, increasing resource consumption and infrastructure cost. Production readiness therefore requires tested HPA thresholds based on actual payment-service workload measurements rather than arbitrary values.
