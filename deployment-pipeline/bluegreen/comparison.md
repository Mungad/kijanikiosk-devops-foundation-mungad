# Deployment Strategy Comparison

This project implemented two deployment approaches for the KijaniKiosk Payments service: blue/green deployment and container-based deployment on Kubernetes. Both methods aim to reduce service disruption during software releases, but they solve different operational problems. Blue/green deployment focuses on switching traffic between two complete application environments, while Kubernetes focuses on maintaining healthy application instances through orchestration and automated recovery.

During the container deployment, the application was deployed with **2 replicas**, allowing traffic to continue even if one instance became unavailable. The production container image was approximately **57 MB**, demonstrating that a multi-stage build can produce a lightweight image suitable for production use.

| Aspect                 | Blue/Green Deployment                                                                                                                              | Container Deployment                                                                                                                                    |
| ---------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Release approach       | Two complete environments exist simultaneously. Traffic switches from the old version to the new version only after verification.                  | A Deployment maintains the desired number of running Pods while Kubernetes schedules and manages the containers.                                        |
| Rollback               | Rollback is performed by directing traffic back to the previous environment. This makes recovery fast because both versions are already available. | Recovery occurs by replacing failed containers automatically. Rolling back to an earlier version requires deploying the previous image tag.             |
| Availability           | User disruption is minimized because only traffic routing changes during release.                                                                  | Availability is maintained by multiple replicas and automated replacement of unhealthy Pods.                                                            |
| Operational complexity | Requires duplicate environments and careful traffic management but provides predictable releases.                                                  | Requires a container registry, Kubernetes manifests, health probes, and cluster management, but offers automated scaling and self-healing capabilities. |

Blue/green deployment provides confidence during releases because the new version is verified before users are directed to it. If monitoring detects a problem after the switch, traffic can immediately return to the previous environment. This approach minimizes customer impact and reduces deployment risk because the earlier version remains available throughout the release process.

Container deployment emphasizes automation and operational resilience. Kubernetes continuously monitors application health using readiness and liveness probes. If a container stops responding correctly, Kubernetes replaces it automatically without manual intervention. Running two replicas also allows one instance to continue serving requests while another is restarted or replaced.

Another important difference is infrastructure utilization. Blue/green deployment temporarily requires two complete environments, increasing infrastructure usage during releases. Container deployment generally uses cluster resources more efficiently because multiple workloads share the same Kubernetes infrastructure. However, Kubernetes introduces additional operational complexity through cluster administration, networking, service discovery, and image management.

The production image was intentionally optimized using a multi-stage build. Build tools and unnecessary files were excluded from the final image, a non-root user was configured for improved security, and a health check was included so Kubernetes could determine whether the application was operating correctly. Producing a smaller production image reduces storage requirements and improves deployment speed because fewer bytes must be transferred from the registry to cluster nodes.

Although Kubernetes provides automated recovery, it is not a complete replacement for careful release management. Health checks verify whether an application is responding, but they cannot determine whether new business logic is correct. A deployment can therefore be technically healthy while still containing functional defects. Blue/green deployment addresses this risk by allowing validation of the new environment before directing customer traffic.

This project also demonstrated the importance of versioned container images stored in a registry. The deployment manifest referenced the exact image tag that had been published previously. Using immutable version tags improves traceability because every deployment can be linked directly to the image that was tested and released. It also makes reproducing earlier releases much simpler when troubleshooting production issues.

## Honest Limitations

This project demonstrates the core deployment techniques but does not represent a complete production platform. The Kubernetes environment consists of a single-node Minikube cluster rather than multiple production nodes, so high availability at the infrastructure level is not demonstrated. The monitoring used during rollback is intentionally simple and is not integrated with centralized alerting or observability systems. Security was also simplified for learning purposes, including the use of an insecure registry configuration within the local development environment. Finally, the workload was tested with basic health verification rather than sustained production traffic, so the measured results should not be interpreted as production performance benchmarks. These limitations are appropriate for demonstrating deployment concepts while remaining honest about what has and has not been validated.
